# phase_limiter の並列化実験と局所依存スケジューリング

## 結論と採用範囲

2026-10-19 に、60秒のステレオ音源で `GradCalculator` の最適化ループを比較した。
採用したのは、**必要な内部区間の処理が完了した境界を TBB のタスクとして投入する方式**である。
原音FFTキャッシュ無効時の追試では、元実装に対して8／16／32スレッドで
それぞれ4.2%／3.0%／6.0%短縮した。キャッシュ有効時にも約3〜6%の改善があった。

また、この環境では `--perf_src_cache=false` が有効で、16／32スレッドでは
有効時より主計算時間が約48〜54%短くなった。キャッシュ有効時だけの結果から、
計算効率やスケジューリング方式の優劣を一般化してはいけない。

本実装は次の範囲に限定する。

- 内部 `oversample == 1` の通常の並列評価・勾配計算で局所依存方式を使う。
- 明示的な直列実行、更新フックのみの実行、内部 `oversample != 1` は従来の経路を使う。
- FFT窓、区間幅、計算回数、FISTA/prox更新とFFTの融合、波形バッファ構成を維持する。
- 評価値・内積・ノルムの集計順序、各サンプルへの勾配加算順序を維持する。
- 実験用の環境変数や方式切替フラグは本実装には設けない。
- `perf_src_cache` の既定値は従来の `true` のまま。今回の高速な条件を使うには
  `--perf_src_cache=false` を明示する。既定値の変更はこのスケジューリング変更に含めない。

対象コードは [GradCalculator.h](../src/phase_limiter/GradCalculator.h)、
回帰テストは [grad_tasks.cpp](../src/test/grad_tasks.cpp) にある。
C++11と既存のlegacy TBBのままで実装している。

## 測定条件と読み方

| 項目 | 条件 |
| --- | --- |
| CPU | AMD Ryzen 9 9950X、16物理コア／32論理スレッド（SMT） |
| OS・コンパイラ | Linux、GCC 12.2、Release、`-O3 -DNDEBUG` |
| SIMD設定 | `SANDYBRIDGE_SUPPORT=ON`、`-march=sandybridge -mtune=sandybridge`、AVX |
| ライブラリ | IPP 2021.9、legacy TBB 2020.3 |
| 基準ソース | `b6a90b83ff555f61b925310f84d9d63111c8ab3a` |
| 入力 | `test_data/test2.wav` を反復して60秒、44.1 kHz、2ch、float WAV |
| CLI | `--disable_input_encode`、指定した `--worker_count` と `--perf_src_cache`、その他は既定値 |
| アルゴリズム | 内部・外部oversample=1、max_iter1=100、max_iter2=400 |
| 比較方法 | 同時実行せず、実行順を変えながら各条件3回または5回。表は中央値 |

初期の会話・ローカル実験メモには「AVX2/FMA」と記載したが、これは誤りだった。
保存済み基準バイナリと通常ビルドのSHA-256が一致すること、およびCMake設定から
上記のAVX設定を確認した。CPU自身がAVX2/FMAに対応することとは区別する。
IPP内部で選択される命令セットは、アプリケーション側のコンパイル設定とは別である。

**主計算時間**は、親プロセスの単調時計でstderrの
`optimizeWithProgressCallback loop start` から
`optimization finished. calc eval func` までを測った実時間。
初期化、最終評価、入出力は含まず、ループ内の集計・判定・ログ出力は含む。
既存の `calcEval`／`calcEvalGrad` のPerformanceCounterはStartごとにリセットされるため、
ループ全体の累積時間としては利用していない。

全体時間はプロセス起動から終了まで。全体時間と主計算時間の差には並列処理も含まれ、
この差をそのまま「直列時間」とは呼べない。

キャッシュ無効の最終追試では、主計算区間のCPU時間も `/proc/PID/stat` から取得した。
これは全スレッドのuser＋system時間の概算であり、スピン待ちも含む。
CPU時間÷実時間は平均何個分の論理CPUを使用したかの目安で、
有効な演算の割合やIPCを表す値ではない。マーカー受信時のサンプリングと時計の粒度による誤差もある。

初期実験はCPUを固定していない。後半のキャッシュ比較・全方式追試では、
16スレッドをCPU 0–15、32スレッドをCPU 0–31に固定した。
このマシンではCPU 16–31が0–15のSMTの相方である。
全方式追試の8スレッドも0–15のマスクを使った。
異なる測定回の小さな差を、厳密な同条件の比較として扱わない。

## 元の並列化と直列部分

元実装は波形を区間に分け、重なるFFT窓の勾配書き込みが競合しないように二段階で処理する。

1. 内部区間の各タスクで、FISTA/prox更新、必要な勾配ゼロクリア、内部FFTを続けて行う。
2. 全内部区間の完了を待つ。
3. 区間の継ぎ目をまたぐFFT窓を、境界グループとして並列処理する。
4. 各グループの結果を決まった順序で合計する。

60秒入力では内部グループ324個、境界グループ322個だった。
TBBの `parallel_for` は複数のグループをまとめて実行し、必要に応じて分割する。
「1 FFT窓につき必ず1 TBBタスク」という粒度ではない。

前処理には波形コピーやバッファ初期化、ループ内には結果集計・ステップ幅や収束の判定・
ログ出力、後処理には出力用コピーなどの直列部分がある。
最適化の反復自体も前回の結果に依存する。波形更新と勾配計算の重い部分は既に並列だった。
最終評価の `calcEval` も並列である。

初期の元実装測定（cache=true、各3回）は次のとおり。

| スレッド数 | 主計算 秒 | 全体 秒 |
| ---: | ---: | ---: |
| 1 | 16.452 | 17.243 |
| 2 | 8.567 | 9.237 |
| 4 | 4.670 | 5.280 |
| 8 | 2.934 | 3.517 |
| 16 | 2.358 | 2.940 |
| 32 | 2.414 | 2.991 |

32論理スレッドは32物理コアではない。16→32で同じコアの実行資源を共有するため、
スレッド数だけを分母にした並列効率には注意が必要である。

## 試した方式

各候補は原則として元実装に単独適用し、複数の改善をまとめて混ぜなかった。

| 方式 | 変更内容 |
| --- | --- |
| affinity | 二つのループにそれぞれ永続的な `affinity_partitioner` を付ける |
| static | `static_partitioner` で分割する |
| 整列 | TaskGroupを64バイト境界に配置する |
| 担当区間・分離版 | 出力勾配の担当区間を固定し、波形全体の更新後にFFT処理。境界FFTは必要な担当ごとに再計算する |
| 担当区間・融合版 | 区間の更新とFFTを同じタスクで実行。境界波形を一度生成して再利用する |
| 局所依存・その場で実行 | 必要な内部区間がすべて完了した境界を、最後の先行タスクのスレッドで実行する |
| 局所依存・タスク投入 | 実行可能になった境界を `tbb::task_group` に投入する。今回採用 |

担当区間方式は16384／32768／65536／131072サンプルの4幅を試した。
融合版では更新前の入力を隣接区間から安全に参照するため、既存の予備バッファ `waveOut` を使う。
波形全体を余分にコピーする処理は追加していない。

分離版でもFISTAの論理更新回数は1回だったが、全域を更新し終えてからFFTで読み直すため、
元の「更新したデータをすぐ使う」局所性を失っていた。融合版はそれを回復した。
ただし境界FFTの重複、境界波形の生成・保存、窓ごとの評価値保存は残る。
論理的な走査回数と、実際のDRAMからの読み出し量は同じではない。

分割統治の発想は「左右の区間を並列処理し、両側が終わった境界を処理する」という依存関係として
検討した。元ソースに無効化された再帰実装の草稿もあったが、グループ対応の懸念が記されており、
そのまま有効化して比較してはいない。今回の局所依存方式は、再帰木を作る代わりに
実際の区間の重なりから依存関係を作る方式である。

| 整列 | +0.03% | −0.19% | −0.55% |

| 方式 | 8スレッド 秒 | 16スレッド 秒 | 32スレッド 秒 |

## `perf_src_cache` の比較

このオプションは原音への窓掛け＋順FFT結果を保持して再利用する。
`false` はそれを毎回計算する。CLIの古いヘルプにはIFFTと書かれているが、対象コードは `dft->Forward` である。

60秒入力で、1／2スレッドは各3回、16／32は各5回。キャッシュ有無と方式を交互に測った。

| スレッド数 | 元実装 true 秒 | 元実装 false 秒 | タスク投入 true 秒 | タスク投入 false 秒 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 16.420 | 14.712 | 16.332 | 14.675 |
| 2 | 8.574 | 7.477 | 8.477 | 7.359 |
| 16 | 2.352 | 1.229 | 2.270 | 1.183 |
| 32 | 2.426 | 1.140 | 2.322 | 1.078 |

無効化で1／2スレッドは約10〜13%、16／32スレッドは約48〜54%短縮した。
32スレッドのタスク投入版の全体時間も2.913→1.608秒となった。
無効時は32スレッドが16スレッドより速い。

別実行で測定した16スレッド・タスク投入版のピークRSSは、trueで約629 MiB、falseで約228 MiB。
FFT結果の保持で約400 MiB増えていた。この条件では、FFTを再計算してでも保持データを減らすほうが有利だった。
メモリ帯域、キャッシュミス、IPCは測定していないため、原因を「DRAM帯域の飽和」とまで断定してはいない。

### CPU時間とスケジューリングの読み取り

32スレッドの主計算区間のCPU時間中央値は次のとおり。

| 方式 | 合計CPU時間 秒 | 平均使用論理CPU数 |
| --- | ---: | ---: |
| 元実装 | 32.12 | 28.10 |
| 担当区間・分離（32768） | 40.52 | 27.58 |
| 担当区間・融合（32768） | 34.42 | 27.10 |
| 局所依存・その場で実行 | 30.19 | 27.71 |
| 局所依存・タスク投入 | 31.49 | 29.24 |

担当区間方式には境界FFTの重複などの追加計算が残る。
局所依存方式では、その場で実行する版がCPU時間を少なく抑え、タスク投入版が実時間を短くした。
後者はより多くの仕事を同時に進める結果になっている。
ただしCPU時間だけで、追加計算とスケジューラやスピン待ちの負担を完全には分離できない。

staticの16スレッドは平均約8.43 CPU分、元実装は約15.01 CPU分だった。
固定分割による負荷の偏りが疑われるが、タスク単位の待ち時間を測って原因を確定したわけではない。

## 採用方式の依存関係と安全性

準備時に、各境界グループについて同じチャンネルかつ区間が重なる内部グループを列挙する。
各内部グループは、その完了によって進む境界の一覧を持つ。
区間の重なりを判定し、配列の添字だけで隣接関係を推定しない。
現在の準備処理は内部数×境界数の比較を一度行い、各反復では構築済みの関係を再利用する。

```text
各境界の残り先行数を初期化
parallel_for 内部区間:
    FISTA/proxなどの更新フック
    内部のFFT・評価／勾配計算
    この内部区間に依存する各境界:
        残り先行数をatomicで減らす
        最後の先行区間なら、その境界をtask_group.runで投入
内部区間と投入済み境界の完了を待つ
元と同じ順序で評価値・内積・ノルムを集計
```

残り先行数の減算は `memory_order_acq_rel`。
最後の先行区間は、それ以前の先行区間による波形・勾配への書き込みも取得してから境界を投入する。
内部グループ同士、境界グループ同士はそれぞれ書き込み領域が重ならず、
内部と境界の重なりだけを依存関係で順序付ける。
そのため、早く実行可能になった境界を始めても、勾配のゼロクリアとの競合や加算順の変更を避けられる。

タスクはフックやバッファを参照で捕捉するため、例外時にも投入済みのタスクをキャンセルして待つ。
処理から戻った後に参照を使うタスクを残さない。依存カウンタは呼び出すたびに再初期化する。

## 検証と限界

研究のCLI比較では、同じ長さの入力に対する出力WAVのSHA-256が一致した。
60秒の最終追試210回はすべて同じ出力で、終了時カウンタは `last_iter=101`、`last_iter2=44`、
ラインサーチ評価は143回だった。300秒入力は別の反復数（142評価）なので、
60秒との処理量が単純に5倍と仮定してはいない。

実験時の補助比較ではfloat32x8／float64x4、長さ1、257、16383、16384、16385、65539、
キャッシュ有無、ノイズ0.1／1e-6、1／2／4／8／16／32スレッドで評価値・勾配の一致を確認した。
既存の窓外末尾の未初期化値の影響を除くため、補助比較では勾配初期値をゼロにそろえた。
60秒CLI測定にはその変更を加えていない。

本実装の回帰テストは、更新フックが入力を書き換え勾配をゼロクリアする条件で、
重なったFFT窓の直列実行と並列実行を比較する。単精度／倍精度、キャッシュ有無、
1／2／4スレッド、短い区間・境界・複数区間、繰り返し呼び出し、フックのみの呼び出し、
例外後の再利用を検証する。

### 本実装への組み込み後の確認

Releaseビルドで追加回帰テストとCTest全10件が通過した。
追加した `GradTasks.*` はASan／UBSan（リーク検出有効）でも通過した。
実験用の環境変数を使わない本実装と、保存済み元実装を60秒入力で各条件3回、計24回比較した。
すべて出力ハッシュと反復数が一致した。16／32スレッドのCPUマスクは前述の追試と同じ。

| キャッシュ | スレッド数 | 元実装 秒 | 本実装 秒 | 短縮率 |
| --- | ---: | ---: | ---: | ---: |
| true | 16 | 2.3904 | 2.2382 | 6.36% |
| true | 32 | 2.4163 | 2.3178 | 4.08% |
| false | 16 | 1.2013 | 1.1805 | 1.73% |
| false | 32 | 1.1467 | 1.0800 | 5.82% |

反復数や実行タイミングによって数%の値は動くが、研究版から本実装への移行で
出力が変わらず、短縮が保たれることを確認した。
組み込み後の記録はローカルの `build/production-validation` に保存した。

単一CPUと単一の反復音源に基づく結果であり、別の曲、FFTライブラリ、CPU、内部oversampleでの
性能一般化はしていない。300秒でのcache=false比較、ハードウェアカウンタ、タスク単位の詳細な
トレースは未実施。測定環境では `perf` がなく、`perf_event_paranoid=4` だった。

## 再現方法と記録の所在

現行実装のビルド・テストはREADMEの依存関係を用意してから実行する。

```sh
cmake --preset release
cmake --build --preset release --parallel "$(nproc)"
ctest --preset release

mkdir -p build/parallel-repro
ffmpeg -y -stream_loop -1 -i test_data/test2.wav -t 60 \
  -ar 44100 -ac 2 -c:a pcm_f32le build/parallel-repro/input.wav
build/release/bin/phase_limiter \
  --input=build/parallel-repro/input.wav \
  --output=build/parallel-repro/output.wav \
  --disable_input_encode --worker_count=32 --perf_src_cache=false
```

研究と同じAVX設定にする場合はconfigureに `-DSANDYBRIDGE_SUPPORT=ON` を付ける。
上記の単発CLI実行だけでは区間時間は集計されない。
主計算の比較では前述のstderrマーカーを親プロセスで時刻記録し、
同一入力・同一ビルド条件・同一CPUマスクで旧版と新版を交互に複数回実行する。
同時に別のベンチマークやビルドを走らせない。出力ハッシュと反復数も比較する。

実験時の未追跡ローカル成果物は `build/` 配下に保存した。
これらはGitには含めず、本書に主要な数値・方式・制約を残している。
クリーンなcheckoutだけでは過去の試作バイナリや実験スクリプトは取得できない。
